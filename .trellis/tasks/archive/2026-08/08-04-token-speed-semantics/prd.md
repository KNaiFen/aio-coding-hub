# Token 速度口径调研与修正

## Goal

让单请求及其聚合统计中的输出 Token 速度只衡量最终成功上游开始产生输出后的生成阶段，不被此前重试、退避或供应商切换等待摊薄。

## Requirements

- 先用采集链路和提交历史证明异常根因，不直接照搬用户给出的候选公式。
- 保留“供应商 TTFB”作为最终尝试的上游首字节延迟，不把重试等待混入该供应商性能指标。
- Token 生成速率直接持久化最终被采用上游流的有效生成持续时间，不再从总请求耗时反推。
- 生成区间从网关收到最终上游流的首个有效增量到最后一个有效增量；流内重试前被丢弃的尝试不计入，前缀缓冲期内收到的增量必须计入。
- 下游放行延迟和背压不能改变供应商速度；无法与下游节奏解耦时必须降级为未知，不能输出被污染的数值。
- AIO 请求卡、实时事件、TUI 请求卡、使用台账/供应商性能趋势等所有请求速度消费者使用同一口径。
- 非流式响应、无输出 Token、缺失/无效时间、未完整采集、流内错误和旧日志必须有显式降级规则。
- 不用简单平均每请求速率；聚合继续使用总输出 Token / 总有效生成时长。

## Acceptance Criteria

- [ ] 回归用例证明：在最终成功尝试前加入任意重试/切换等待，不会改变相同最终流的 Token/s。
- [ ] 最终成功供应商生成变慢时，Token/s 会按新口径正确变化；首 Token 延迟仍只影响 TTFB。
- [ ] AIO、TUI、实时事件和聚合 SQL 对同一请求得到一致速度。
- [ ] 旧数据没有新时间证据时使用明确的兼容回退，不伪造高精度结果。
- [ ] TTFB 展示和供应商 TTFB 聚合保持最终尝试语义。
- [ ] 本地只运行前端/TypeScript 验证；Rust 与绑定漂移由 GitHub Actions 验证。

## Locked Direction

- `ttfb_ms` 与 `visible_ttfb_ms` 保持现有职责，不参与新 Token/s 分母。
- 新增版本化的 `upstream_stream_duration_ms`，表示最终被采用上游流首尾有效增量的间隔。
- Token/s 只在 `upstream_stream_timing_version = 1` 时使用 `output_tokens / upstream_stream_duration_ms`；历史与不可可靠采集的记录不回退到旧公式。
