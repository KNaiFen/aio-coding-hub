# Provider 日汇总与 ledger 合同调查

## 触发证据

- UPA-008 候选分支的云端百万行 release 基准测得 Provider 性能趋势查询
  `5.057927737s`，超过 `1s` 合并门禁。
- 当前趋势查询为选择 Top Provider 和分桶聚合两次扫描 `usage_events`；继续依赖
  百万行逐请求 ledger 无法给出可信的五倍优化承诺。

## 既有数据合同

`request_logs` 保存请求详情并受 `request_log_retention_days` 控制；
`usage_ledger` 是长期分析事实源。后者不仅服务趋势，还被以下行为读取：

- 总览和 CLI、Provider、模型、日期排行榜；
- 小时统计、文件夹和 Session 聚合；
- Provider 首次使用时间、限额窗口和成本统计；
- 缺失成本修正；
- Provider 删除、手动清空统计和历史名称快照。

因此，把 `usage_ledger` 直接压成“每 Provider 每自然日一行”并删除逐请求行，会丢失
模型、Session、文件夹、成本修正和精确自定义时间范围所需的维度。这不是仅丢失请求
详情，而是 fork 现有产品行为回归。

## 本任务采用的安全边界

1. 新增可重建的 Provider 日汇总投影，保存趋势所需的请求计数、有效样本数、耗时、
   TTFB、输出速率和缓存 Token 累计值。
2. 日汇总只以 `usage_ledger` 为事实源；不查询 `request_logs`，不改变详情保留设置。
3. 已完成的本地自然日由后台有界回填，当前未完成自然日继续读取 raw ledger，从而保留
   小时级趋势。
4. 趋势查询组合“已覆盖日汇总 + 未覆盖 raw ledger”，并以持久化覆盖游标避免重复计数。
5. `usage_ledger` 在本任务中继续保留，因为仍有多个非趋势消费者。物理删除必须先把
   这些消费者迁移到维度完整的历史投影，应作为独立产品改造处理。
6. 日汇总是派生缓存，可以从 ledger 重建；回填或刷新失败不得删除事实数据，也不得
   阻断网关启动。

## 验证要求

- 回填可恢复、幂等，事务提交前不得推进覆盖游标。
- 新写入和已完成日边界不得重复或漏计；本地时区/DST 边界需要测试。
- Provider 名称快照、CX2CC 排除、显式 Provider 和 Top 10 排名保持一致。
- 原始 ledger 与日汇总混合结果必须等于纯 ledger 结果。
- 百万行 release 基准必须包含日汇总回填与查询，并且查询不超过 `1s`。
- Provider 删除并清空统计时同步删除日汇总；不清空统计时保留历史快照。

## 后续物理压缩前置条件

若未来要删除已汇总的 `usage_ledger` 行，必须先决定并实现模型、Session、文件夹、
成本修正和部分日自定义范围的历史语义，再迁移所有 `usage_events` 消费者。单一
Provider 日汇总无法无损替代这些维度。
