# 技术设计

## 数据流与边界

```text
设置 UI -> settings_set 严格校验 -> AppSettings v57
                                      |
原始上游 4xx/5xx -> 有界错误体观察 -> 规则候选（只读）
                                      |
重试/切换/熔断完成 -> 最终候选 -> 客户端协议响应 -> 主日志
                         |                    |
                    尝试链保留上游状态   special_settings_json 标记
```

普通设置写入新增字段 `upstream_error_response_rules`，字段所有权由
`settings_set` 持有，并在共享设置锁内完成校验和提交。设置版本升至 57，
默认空数组；磁盘反序列化采用逐条容错，非法条目不进入运行时。

## 规则契约

每条规则包含稳定 UUID、名称、说明、启用状态、`0..=9999` 优先级、最多 16
个 400–599 状态码、最多 16 个关键词、Any/All、CLI 范围、供应商 ID 范围，
以及状态和消息两个带标签的 `passthrough` / `override` 行为。最多 32 条规则。
名称最长 100，说明最长 256，关键词最长 512，自定义消息最长 4096 字符。

状态组内部 OR，关键词组内部 OR；Any 表示任一已配置组匹配，All 表示所有已
配置组匹配。至少配置一个条件组。空 CLI/供应商范围分别表示全部；两者均非空
时同时满足。规则按优先级和列表位置排序，只采用首个命中项。

## 终态响应处理

规则观察复用现有错误响应正文读取与 64 KiB 上限，不增加无界读取。候选使用
原始上游状态、CLI 和实际供应商身份，只存放最终尝试所需的有界元数据。任意
后续成功、不同失败或网络错误都会替换/清除先前候选。

改写只发生在原有终态决策之后。状态透传使用最终上游状态；消息透传依次读取
`error.message`（含 JSON 字符串）、`detail`、顶层 `message`、字符串
`error` 和有限纯文本。无法得到消息时不做部分改写，完整退回原响应。

Claude 使用 `{type:"error",error:{type:"upstream_error",message}}`；
Codex/Grok 使用 `{error:{type:"upstream_error",code:"upstream_error",message}}`；
Gemini 使用 `{error:{code,status:"UNKNOWN",message}}`。通过 serde 构造 JSON，
清除失效实体头，保留安全的追踪及重试提示头。

## 失败隔离与审计

匹配器是无错误出口的纯观察函数，禁止 panic、正文日志和路由副作用。设置写入
严格拒绝非法数据，设置读取则逐条丢弃无效数据。规则运行异常、正文不可检查或
协议构造失败均返回原有响应。

主请求日志记录客户端最终状态，尝试链保留上游状态与现有分类。命中时向
`special_settings_json` 追加固定大小标记，仅含规则 ID/名称、供应商 ID/名称、
改写前后状态和行为模式。首页与日志卡片显示徽标，提示展示这些审计字段；不
持久化响应正文、关键词、提取消息或自定义消息。

## 参考实现取舍

Sub2API 的优先级、Any/All、平台范围、消息提取和协议包装作为行为参考；AIO
不引入其缓存、数据库表或跳过监控功能。AIO 是本地单进程应用，直接沿用现有
AppSettings 快照和异步请求日志写入。
