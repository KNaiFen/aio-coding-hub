# 悬浮窗计数分区与限额前置路由

## Goal

让 Tray 悬浮窗中的成功/失败计数具有清晰分区，并让已达到限额的供应商在本次请求路由中表现得与关闭供应商一致，避免无效的高优先级命中、假重试和会话复用丢失。

## Requirements

- Tray 原生逻辑宽度保持 404px；成功和失败计数之间增加细分割线与稳定留白，不改变计数精度、缩写或无障碍文本。
- 已知 OAuth 配额耗尽或配置消费限额已达的供应商，在强制候选收窄后、会话绑定解析前从本次候选列表排除。
- 限额排除不修改供应商持久化 `enabled`；额度恢复后，下一个请求自动恢复候选资格。
- 限额排除不产生 skipped attempt，不消耗 Ready-provider、provider、attempt 或 retry 索引。
- 过滤后存在可用候选时，保持原路由优先级；直接请求第一个可用候选，并允许已绑定的低优先级候选命中会话复用。
- 过滤后候选为空时，严格采用空路由语义：HTTP 503、`GW_NO_ENABLED_PROVIDER`、空 attempts、无 `Retry-After`。
- 强制供应商和托管模型仍不得跨候选回退；其唯一候选限额时同样采用空路由语义。
- 发送前保留限额复查以覆盖并发竞态；若复查后全部候选仅因限额被排除且没有真实尝试，仍采用空路由语义。
- 熔断、冷却、运行时全局关闭及真实上游失败继续沿用既有审计与 failover 行为。
- 首次未知的真实上游 429 仍是一次真实尝试；额度快照落盘后的后续请求才前置排除。

## Acceptance Criteria

- [ ] 截图中的 `成 624` 与 `败 8` 分属两个固定区域，中间有浅色竖线与留白，404px 窗口内不溢出。
- [ ] 高优先级限额、低优先级可用时，高优先级供应商零上游调用，低优先级成功 attempt 的 `attempt_index` 与 `provider_index` 均为 1。
- [ ] 上述请求不再显示 `重试 1`；若低优先级供应商已有有效 Session 绑定，则显示会话复用。
- [ ] 旧绑定指向限额供应商时先清理，成功切换后重绑；下一同 Session 请求复用新供应商。
- [ ] 全部候选限额时返回 `GW_NO_ENABLED_PROVIDER` / HTTP 503，attempts 为空且没有 `Retry-After`。
- [ ] 限额与熔断/冷却混合时，非限额候选仍由共同 gate 审计并按现有 unavailable 语义收口。
- [ ] 前端目标测试、全量 Vitest、TypeScript、ESLint、Vite build、格式检查通过；Rust 和原生检查由 GitHub Actions 通过。
- [ ] PR 在合并前同步最新 `origin/main`，重新通过必需 CI，且不覆盖其他 worktree/PR 已进入主线的改动。
