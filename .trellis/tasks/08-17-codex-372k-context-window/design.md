# Codex 372K 上下文开关设计

## Context

The requested behavior is model-specific catalog policy, not a global Codex root override. The repository already builds one complete managed `model_catalog_json` for profile routing, preserves unknown fields, records ownership hashes, and restores the original catalog pointer. The new preference must extend that single lifecycle and must also work when the CLI proxy or managed profiles are inactive.

The prerequisite task `08-17-codex-config-transaction-hardening` establishes the canonical/live config transaction used here. This task must not recreate that infrastructure.

## Authoritative State And Command Boundary

Persist one backend-owned AIO preference such as `codex_372k_context_window_enabled`. Expose a dedicated Tauri command/query contract whose mutation accepts only `enabled: bool` and returns authoritative state. Do not expose model slugs, numeric limits, file paths, or raw catalog data as frontend-controlled mutation parameters.

The frontend switch:

- reads authoritative state with the Codex settings query;
- disables while the dedicated mutation is pending;
- uses the existing serialized Codex mutation scope and toast/error conventions;
- does not call `refreshCodex`, restart Codex, or add an effectiveness notice after success.

## Base Catalog Selection

Under the shared Codex lifecycle transaction:

1. Resolve the canonical direct configuration.
2. If its original user `model_catalog_json` is an absolute safe path, read that complete JSON within the existing size limit.
3. Otherwise invoke the installed Codex executable with structured arguments for `debug models --bundled` and parse its complete output.
4. Never inspect or fall back to `models_cache.json`.

The base identity and content hash join the catalog ownership metadata. A changed base is drift that requires an intentional rebuild, not silent reuse of stale generated bytes.

## Pure Catalog Composition

Use a structural JSON transform with a fixed target set:

```text
gpt-5.6-sol
gpt-5.6-terra
gpt-5.6-luna
```

For each exact slug, replace only:

```text
context_window = 372000
max_context_window = 372000
```

Do not assign, normalize, delete, or synthesize `effective_context_window_percent`; copying the model object preserves it. Do not change any auto-compaction field. Require exactly one structurally valid entry for each target before producing output so partial target application cannot occur.

Composition order is fixed:

1. complete current base catalog;
2. optional 372K transform of the three built-in models;
3. optional managed-profile rows and capabilities;
4. AIO ownership metadata/hash over the resulting payload and active policies.

This order keeps profile rows independent from the three built-in targets and makes one output deterministic.

## Activation And Deactivation

Catalog activation is no longer equivalent to “managed profiles are non-empty”. It is active when either:

- the 372K preference is enabled; or
- managed profiles require generated rows.

Enable transaction:

1. capture the prior canonical catalog pointer or absence and config baseline through the prerequisite coordinator;
2. build and atomically write the owned complete catalog;
3. project `model_catalog_json` into canonical/live config as appropriate;
4. commit preference and ownership manifest together.

Disable transaction:

- with active profiles: rebuild one owned catalog from the same base without the 372K transform and retain its pointer;
- without active profiles: restore the prior pointer or delete the AIO-added key, then remove only an ownership-verified generated catalog;
- with external drift: stop and return recovery-required rather than overwrite.

Repeated transitions are idempotent. Restart reconstructs intent from the persisted preference and manifest under the same transaction coordinator.

## Backup, Ownership, And Failure Handling

- Extend the existing catalog owner schema/generation rather than adding another manifest that can race it.
- Include active policies, base hash, prior pointer, output payload hash, and transaction generation.
- Validate all source and output paths with existing bounded-read, symlink/reparse, and atomic-write protections.
- Apply compare-before-write and compare-before-rollback semantics from the prerequisite.
- Avoid logging catalog contents, config bytes, environment values, or user paths beyond the repository's current redacted diagnostics.

## Runtime Verification Boundary

There is deliberately no post-toggle proof step. The implementation does not:

- refresh the Codex model catalog;
- launch Codex or make a model request;
- scan the generated catalog again to announce `372000/372000/95`;
- expose a health badge claiming the values are active.

Unit and integration tests assert only that AIO planned and wrote the requested owned artifacts. Delivery language must retain that distinction. User real-world feedback is the only requested runtime signal.

## Verification Design

Pure JSON tests deep-compare every non-target value and assert exactly six target differences. Temp-home tests cover user/bundled bases, enable/disable/profile/proxy/restart combinations, drift and failpoints, prior-pointer restoration, and an untouched `models_cache.json` sentinel. Frontend tests assert toggle state/mutations and prove no `refreshCodex` call. None of these tests claims that Codex adopted 372K at runtime.

Repository policy forbids ordinary local dependency, Cargo, frontend, test, build, or binding-generation commands. Local evidence comes from `$gkd-local-verify`; CI owns generated-binding validation and the full test matrix.
