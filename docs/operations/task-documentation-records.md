# 任务方案与实施结果留痕规范

本规范确保 main 与用户已经确认并进入实施的改动方案，以及最终实施结果，都有仓库内 Markdown 记录。它不要求保存每段聊天，也不要求所有任务创建 worktree。

## 何时必须记录

满足以下条件时，main 必须在修改代码或文档前落下“确认方案”：

- main 与用户已经明确要解决的问题、目标和主要边界。
- 用户已经授权进入实施，而不只是讨论、评估或加入 `PENDING.md`。

任务结束前必须补充“实施结果”，无论结果是完成、部分完成、失败、阻塞或明确放弃。

以下内容不要求单独记录为实施方案：

- 尚未收敛的头脑风暴。
- 只回答问题、解释代码或做只读审计的交流。
- 用户只要求登记到 `PENDING.md`、但尚未授权实施的事项。

聊天记录不能替代仓库文件。聊天中确认的用户决定、范围变化和验收标准，应同步到对应 Markdown。

## 方案确认与变更

确认方案不是“已经讨论过”的同义词。它必须在最前面留下足以让后续 session 判断能否开工的简短事实：

- **实施授权**：`待确认` 或 `已确认`；已确认时记录日期、确认摘要和覆盖的范围、锁定决定、验收标准。
- **方案版本**：规划提交的完整 SHA；简单任务没有独立提交时记录同月条目日期。`execution.md` 只引用该版本，不复制确认内容。
- **事实、假设与未决问题**：只列会影响范围、设计或验收的事项，注明来源（用户、现行规范、代码或外部证据）和关闭条件。材料性未决问题未关闭时不得进入实施。

计划在实施中变化时，在原记录追加一条“范围与决定变更”：日期、原/新决定、受影响的验收标准或验证、原因/证据、决定人和恢复条件。影响用户行为、兼容性、范围或验收标准的变化必须重新获得用户确认；main 的技术判断不能替代用户对产品范围的授权。

## 任务分流

### 简单任务：main 直接实施

同时满足以下特征时，main session 可以直接在 `main/` 检出中完成，不创建额外 worktree：

- 不交给独立执行 session，也不需要与其他 session 并行施工。
- 范围小、影响边界清楚，可以在一个连续工作阶段内完成和复核。
- 不涉及仍未确认的产品决定、高风险迁移或大范围跨模块设计。
- 当前 main 检出中的已有修改归属明确，不会把用户工作混入本任务。

远端 `main` 受保护时，main session 仍使用短期 PR 分支交付；“直接 main 实施”表示由 main session 在 `main/` 目录施工，不表示绕过 PR 或直接推送远端 `main`。

简单任务在当月的 `docs/history/change-records/YYYY-MM.md` 增加一个条目，同一条目包含“确认方案”和“实施结果”。使用 [简单变更记录模板](./templates/simple-change-record.md)。

若简单任务实施中扩大为委派或 worktree 任务，保留原条目并标记“已迁移”，记录迁移原因、冻结提交或未提交修改的处置，以及新任务目录链接。新任务的 `prd.md` 或 `execution.md` 反向链接该条目；从此只有任务 worktree 的材料是详细活动方案。

### 复杂、并行或委派任务：独立 worktree

出现以下任一情况时，由 main 创建同级 worktree：

- 任务交给独立执行 session。
- 多个任务需要并行，或任务会跨越较长 session。
- 变更范围大、风险高、跨多个模块，或需要隔离工作状态。
- 与其他活动任务存在依赖、合并顺序或潜在冲突。

这类任务按 [多 Worktree 任务交付规范](./multi-worktree-delivery.md) 工作。所有独立执行任务在开工前需要 `prd.md` 和 `execution.md`，声明可验收前需要 `delivery.md`；复杂任务再增加 `design.md` 和 `implement.md`，验收失败时才创建 `findings.md`。

任务开始时看起来简单、实施中却明显扩大时，main 应保留已有记录，暂停修改并把任务迁移到独立 worktree，不要为了维持“简单任务”标签继续堆叠风险。

## 确认方案必须包含

无论使用简单记录还是完整任务包，都应让后续 session 明确：

- **问题与目标**：为什么改、期望改变什么行为。
- **方案状态与版本**：是否已获实施授权、确认覆盖内容和规划提交/记录入口。
- **范围**：必须完成、允许触碰和明确不处理的内容。
- **用户锁定决定**：不能由实现者自行改变的产品行为、优先级或取舍。
- **事实、假设与未决问题**：材料性推断的来源、状态和关闭条件。
- **实现方向**：主要模块、接口、数据流或修改位置；简单任务可以简写。
- **验收标准**：可以观察或验证的完成条件。
- **验证计划**：允许的本地检查、必需 CI/编译和人工验证。
- **风险、依赖与 PENDING 审阅**：兼容性、迁移、并行任务、相关 PENDING ID 的纳入/延后结论，以及需要暂停询问的条件。

Plan 模式必须主动定位代码和现状，把能从仓库确认的技术事实查清。对用户意图、产品行为、优先级、取舍或成功标准不确定时，必须询问用户，不能把猜测写成确认方案。

## 实施结果必须包含

任务结束前记录实际发生的事情，而不是复制原计划：

- **结果状态**：完成、部分完成、失败、阻塞或放弃。
- **实际实现**：行为变化，以及关键文件、模块或符号。
- **验收对应**：每条主要标准是否满足及证据。
- **方案偏移**：原计划与实际实现的差异、原因和影响。
- **验证结果**：真实执行的本地检查、PR CI、编译和人工验证；未运行项及原因。
- **交付证据**：PR、提交、发布或其他可追溯入口。
- **文档与合同**：同步更新的位置，或明确不适用。
- **遗留事项**：风险、阻塞、未完成内容和后续决定。

委派任务还必须由 main 在 `delivery.md` 留下验收轮次、审查的 PR head SHA、CI 证据和结论；有功能 PR 时在其合并后、没有功能 PR 时在终态文档 PR 中，在同一文件的收尾区记录最终结果、实际存在或不存在的 merge commit、归档、知识库、PENDING 和清理事实。阻塞任务保持活动，不伪造合并或归档证据。

不得把当前范围内未完成的内容隐藏为“以后优化”，也不得编造未执行的测试或 CI 结果。

## 维护责任

- main 负责在实施前确认 Markdown 计划已经落盘，在合并或结束前确认结果已经补齐。
- 执行 session 负责维护 `delivery.md`；main 负责简单任务记录、验收意见和最终知识库同步。
- 计划变化时更新原记录，并保留足以解释偏移、确认和恢复条件的原因；不要让聊天中的新决定覆盖文件而不落盘。
- 记录随对应 PR 一起进入 main。失败、阻塞或放弃且没有功能 PR 时，main 仍应通过一个只包含记录的文档 PR 保存结论。
- main 在规划时记录相关 `PENDING.md` ID 的处理结论；完成项只在合并、验证和证据齐全后迁入完成历史，部分完成项保留并重写剩余范围，放弃项必须引用用户的明确决定。
- 简单变更月度记录是历史证据，不是现行规范；可复用的长期知识必须另行更新 `docs/`、`AGENTS.md` 或 `.trellis/spec/`。收尾时至少判断：用户可见行为、公共 API/合同、架构决定、迁移/配置、运维流程和可复发陷阱；只把稳定结论写入知识库，一次性过程留在任务记录。
